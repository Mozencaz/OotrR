## 2. Performance : génération de seed

### 2.1 [P0, 2 lignes] Tables de chaînes BYML quadratiques — **−43 % mesuré**

`formats/byml_codec.py:39` et `formats/inspect_resources.py:54` :

```python
data[off + u32(off + 4 + i * 4):].split(b'\0', 1)[0]
```

Chaque chaîne **copie tout le reste du buffer** avant de couper. Sur `RSDB/ActorInfo` (1,9 Mo, 10 692 chaînes) : **4,75 s → 2 ms**. Sur `Effect/static...vsetb` (51 Mo) : 12,8 s → 0,6 ms. Sur 1 847 fichiers BYML du jeu : 37 s → 0,05 s.

```python
starts = [off + u32(off + 4 + i * 4) for i in range(u24(off + 1))]
return [data[s:data.index(b'\0', s)].decode() for s in starts]
```

Testé sur une copie du code : génération 68 → 39 s, verify 33 → 18 s, `romfs/` identique octet par octet, seed identique. Ça accélère aussi `scan_world`, la construction de l'apworld, le tracker et tous les tests NUP.

### 2.2 [P1] Un `ResourceStore` unique au lieu de `extra_raw.get(p) or decompress(read(p), d)`

`randomizer_core.py` contient **75** `decompress(read(...))` et **35** `extra_raw.get(...)`, plus 9 lambdas `current_raw`/`watch_raw`/`current_flow`/`tracking_read`… qui font toutes la même chose. Il y a aussi trois dictionnaires parallèles (`raw_maps`, `extra_raw`, `plain_raw`) plus `files`, `new_files`, `modified`, `new`.

Conséquences :
- un même fichier est relu dans le NUP, re-hashé (sha256 dans `Nup.read` **et** dans `source_reader`) puis re-décompressé à chaque accès (ex. `CHALLENGES` et `EVENT_SETTINGS`, décompressés au moins 4 fois chacun) ;
- c'est fragile : `extra_raw.get(path) or …` traite un `b''` comme absent, et oublier de passer par `extra_raw` écrase silencieusement le patch d'avant ;
- `(de)compress or not` est décidé au cas par cas avec `path.endswith('.zs')`.

Proposition (`formats/resource_store.py`) :

```python
class ResourceStore:
    """Vanilla resources read once, current state, and changes to write."""
    def __init__(self, nup, members, dictionaries): ...
    def vanilla(self, path) -> bytes          # décompressé, en cache, sha recordé dans sources
    def raw(self, path) -> bytes              # état courant (modifié sinon vanilla)
    def set(self, path, raw)                  # marque comme modifié
    def byml(self, path) -> dict              # document parsé en cache ; invalidé par set()
    def flow(self, path) -> evfl.EventFlow    # idem
    def new(self, path, raw, template)        # nouveaux fichiers (RESTBL)
    def changed(self) -> dict                 # pour compress/RESTBL/manifest
```

Le store sait si un chemin est compressé (`.zs`) ou brut. Il remplace `read`, `compress`, `raw_maps`, `extra_raw`, `plain_raw`, `modified`, `new`, et toutes les lambdas.

### 2.3 [P1] Garder les documents parsés plutôt que des octets entre deux patchs

Les patchs se passent des `bytes` : chacun parse, modifie et re-sérialise. Exemples :
- **GameData** passe par environ 12 étapes (`kakariko_burning_on_medallions`, `sheik_temple_expression`, `scene_expressions`, `membership_expressions`, `door_song_condition`, `apply_openings`, `add_saved_flags` ×3, âmes, clés, flags répétables…). Chacune coûte environ 0,6 s de parse et 0,3 s de dump.
- **`ACTION_GUIDE_FLOW`** est parsé et réécrit 4 fois (guide ocarina, clés, convertisseur progressif, évasion de Zelda…).
- `complete_event_info` et `event_info._chart` reparsent des flows déjà parsés par le patch précédent (6 178 appels à `_chart`).

Avec `store.byml(path)` / `store.flow(path)` qui renvoient un objet mutable en cache et ne sérialisent qu'une fois, à la fin (`store.changed()`), les patchs migrent un par un : un adaptateur `bytes → bytes` reste possible pendant la transition.

Gain attendu : 10–15 s sur les 39 s restantes.

### 2.4 [P1] Mettre en cache `scan_world` sur disque, par empreinte du NUP

`scan_world` (≈ 7 s réelles) dépend uniquement du jeu. Il est refait par chaque génération, par `verify`, par la construction de l'apworld et par 14 modules de test.

- Clé : `sha256(TOC du NUP) + version du scanner` (le TOC est déjà hashé dans `Nup.__init__`).
- Valeur : `groups, enemies, extra` en JSON compressé (pas `maps`, qui contient des données du jeu ; `maps` peut rester paresseux, voir plus bas) dans `data_dir()/cache/`.
- `bridge.scan_fingerprint` existe déjà : il peut servir de contrôle d'intégrité.

`maps` sert ensuite à la composition, mais seulement pour les ressources réellement modifiées : on peut le charger à la demande via le store.

### 2.5 [P2] Petits gains rapides

- `decompress()` (`inspect_resources.py:26`) reconstruit un `ZstdCompressionDict` et un `ZstdDecompressor` **pour chaque dictionnaire à chaque appel**. `recompress()` fait pareil. Il faut un cache `dict_id → (compressor, decompressor)` créé une fois par NUP.
- `Nup.read` vérifie le sha256 du membre à chaque lecture, et `source_reader` le recalcule. Le store évite déjà les relectures ; on peut aussi ne vérifier qu'une fois par membre.
- `effective_members` trie toutes les entrées du NUP deux fois (une par package). Un seul tri suffit.
- `Logic.compile` : **1 897 règles, 477 uniques**. La moitié du temps part dans `copy.deepcopy` d'AST et `check_generated`. Un cache `source → lambda` au niveau du module (et `rule → code`) ramène `Logic()` d'environ 0,7 s à 0,15 s, ce qui compte surtout pour les tests et le tracker.
- Compression zstd niveau 10 (4,4 s) : à mesurer au niveau 3–6. La taille ne joue que sur la RESTBL, qui est déjà agrandie au besoin.
- `messages = sorted(m for m in members if m.startswith('Mals/') and '.Product.110.' in m)` est recalculé 5 fois. Une propriété du store suffit.

### 2.6 [P2] `verify`

`verify` refait une partie du travail de `generate` (scan, reconstruction des éditions attendues, relecture des flows). Une fois §2.1–2.4 en place, il bénéficie du cache de scan et du store. Il faut garder son indépendance (il ne réutilise pas le plan) : le cache contient des données du jeu, pas des décisions du générateur, donc ça ne pose pas de problème.

`test_progressive`, `test_item_forms`, `test_song_models`, `test_master_sword_item`, `test_door_song_condition` passent presque tout leur temps à charger ActorInfo/RSDB. On peut attendre environ −40 % sur la suite NUP.

### 3.2 [P1] Fixtures partagées pour toute la session

Aujourd'hui chaque module ouvre son `Nup`, relit les dictionnaires et refait `scan_maps`/`scan_world` dans son `setUpClass` (14 modules).

- `tests/game_fixture.py` : `nup()`, `dictionaries()`, `members()`, `scan()`, `store()` mémoïsés au niveau du module Python (une seule fois par processus), plus le cache disque du §2.4.

### 3.3 [P1] Paralléliser

La suite est en `unittest` pur et les modules sont indépendants. Deux options :
- `pytest -n auto` (pytest-xdist) : il exécute les `unittest.TestCase` tels quels, sans rien réécrire ;
- ou `unittest-parallel`.

Sur 8 cœurs, la suite NUP passerait d'environ 7 min (après §3.1) à environ 1,5–2 min. Le fichier de cache du §2.4 doit être écrit de façon atomique (`tmp` + `rename`), comme `publish_mod` le fait déjà.

### 3.4 [P1] Faire tourner les tests logiques en CI sans le jeu

**En CI, 319 tests (32 %) ne tournent jamais**, dont toute l'intégration placement/logique. Le jeu n'est pas distribuable, mais le **catalogue des sources l'est déjà** : l'apworld embarque `groups/enemies/extra` (identifiants, hashs, positions, sans aucun asset).

- Committer `tests/fixtures/scan_v131072.json.zst` (le même catalogue que l'apworld) ;
- `test_full_randomizer`, `test_extra_sources`, `test_archipelago`, `test_start_options`, `test_soul_logic`… l'utilisent quand `OOT_NUP` est absent ;
- seuls les tests de *fichiers* (patchs BYML/evfl réels) restent liés à `OOT_NUP`.

### 3.5 [P2] Divers

- `test_rules.test_the_tracker_rebuilds_the_logic_from_the_stored_settings` (6,8 s) : il recompile probablement plusieurs `Logic`, à couvrir par le cache §2.5.
- Les erreurs Tk `invalid command name "...poll"` / `tracker_tick` en fin de tests GUI sont des callbacks `after()` non annulés avant `destroy()`. C'est sans effet mais ça pollue la sortie : il faut garder l'id de `after()` et faire `after_cancel` dans `tearDown`.
- Ajouter un job CI `durations` (`pytest --durations=20`) pour repérer les régressions de temps.

## 4. Refactorisation et mutualisation

### 4.1 [P1] Découper `generate()` (620 lignes) en pipeline de patchs déclaratifs

`randomizer_core.generate` (l. 342–962) et `_build_full` (l. 965–1306) enchaînent environ 60 étapes à la main, avec **82 imports locaux**. Les étapes ont trois formes de retour (`raw`, `(raw, details)`, `[(path, fix)]`, `apply(existing, generated, read)`) et des dépendances d'ordre implicites, écrites seulement en commentaire (« Apply last », « After the sub-flow completion above », « Before the castle requests »).

Proposition (`randomizer/pipeline.py`) :

```python
@dataclass(frozen=True)
class Step:
    name: str                          # clé dans manifest['skips']
    enabled: Callable[[Context], bool]
    apply: Callable[[Context], object] # modifie ctx.store, renvoie le détail du manifest
    after: tuple[str, ...] = ()        # dépendances explicites, vérifiées

STEPS = [
    Step('title_badge', always, title_badge.step),
    Step('save_warp', always, save_warp.step),
    Step('kokiri_shop', full_mode, kokiri_shop.step),
    Step('story_fixes.lost_dog', full_mode, lost_dog.step),
    ...
    Step('chest_flags', full_mode, chest_flags.step, after=('event_info', 'ap_mailbox')),
    Step('bomb_refills', always, bomb_refills.step, after=('*',)),
]
```

`generate()` devient : valider → `Context(store, settings, plan)` → exécuter `STEPS` dans l'ordre topologique → compresser/RESTBL → manifest → publier. Ça représente environ 80 lignes.

Bénéfices :
- un patch = un module + une ligne dans `STEPS` (aujourd'hui il faut 3 endroits dans `generate()` et un dans `skips`) ;
- chaque patch se teste isolément avec un `Context` factice (aujourd'hui `test_randomizer_core` doit vérifier par AST que les noms de `generate()` sont importés, ce qui montre bien la fragilité) ;
- `verify` peut parcourir la même liste pour savoir quels fichiers ont le droit de changer ;
- `qol_install` peut sélectionner un sous-ensemble des mêmes `Step` (à vérifier : je n'ai pas lu son code en détail).

À migrer par petits lots (story_fixes, puis QoL, puis Archipelago, etc.), en vérifiant à chaque lot que le romfs généré reste identique octet par octet (voir le harnais au §6).

### 4.2 [P1] Factoriser les motifs répétés dans `_build_full`

- `modified[path] if path in modified else decompress(read(path), d)` apparaît 12 fois (`key_read`, `token_read`, `ap_read`, `repeat_read_raw`…) : c'est `store.raw(path)`.
- Le bloc « messages + `build_X_files(read, items, messages)` + `modified.update` + `new.update` » est identique pour âmes, clés, items AP, jetons, harpes. Il faut une interface commune `build_files(store, items)` (`soul_adapter`, `key_adapter`, `ap_item`, `progressive`, `song_models` partagent déjà `soul_adapter.build_item_files`).
- `npc_gifts` est reconstruit à l'identique dans `generate` (l. 499) et `verify` (l. 80) : une fonction suffit.
- La boucle de `story_fixes` (zora river adulte/enfant, lake tree, bombchu shop) répète « lire map → edits → `patch_strings` → `story[...]` ». Elle devrait vivre dans `story_fixes` comme une liste `(map, edits_fn, key)`, sur le modèle de `flow_fixes()` / `scene_module_fixes()`, qui existent déjà.

### 4.3 [P2] Utilitaires mal placés

- `murmur3` est défini dans `patching/soul_adapter.py` et importé par **15 modules** (tracker, archipelago, GUI…). Il faut le déplacer dans `formats/hashing.py` avec `sha256` (aujourd'hui dans `patching/qol_patches.py`, importé par le cœur).
- `effective_members` est dans `game/world_maps.py` et `decompress`/`dictionaries` dans `formats/inspect_resources.py`. Ils vont dans `formats/nup.py` (ou dans le store).
- Le préfixe des drapeaux de check `'RandoCheck.' + settings_identity(settings)[:16] + '.' + gid` est construit en dur dans `_build_full` et dans `verify`. Une seule fonction suffit.
- `Logic.sweep(record_spheres=...)` est un paramètre mort (`pass`).
- `randomizer_core.py:982` : condition `if` sur une ligne de plus de 200 caractères (un saut de ligne a été perdu).

### 4.4 [P2] GUI : `Application` fait 2 050 lignes dans un seul fichier

`gui/randomizer_gui.py` (2 341 lignes, 115 méthodes) mélange construction des widgets, état des options, génération, tracker, Archipelago et mises à jour. Les options sont déjà déclaratives (`rando_options.Option`), ce qui est un bon point. Découpage naturel, sur le modèle de `parties_page.py`, déjà extrait :
- `gui/options_page.py` : rendu générique des `Option` par onglet ;
- `gui/generate_page.py` : choix NUP/dossier, génération (`generation_worker`) ;
- `gui/tracker_page.py`, `gui/archipelago_page.py` ;
- `Application` ne garde que la fenêtre, la navigation et les préférences.

### 4.5 [P3] `verify.verify` fait 840 lignes dans une seule fonction

Il faut le découper en vérifications nommées (`check_maps`, `check_events`, `check_chest_flags`, `check_mailbox`, `check_logic`…), chacune renvoyant son entrée de rapport. Ça devient trivial une fois le pipeline §4.1 en place.

## 5. Efficacité du flux de travail

### 5.1 [P1] Bug de déterminisme : `tracking.json` change d'une exécution à l'autre

Deux générations identiques produisent un `romfs/` identique, mais `tracking.json` (et donc `manifest.tracking.sha256`) diffère : l'ordre des clés de `logic/locations` dépend de l'itération d'un `set` (hash aléatoire par processus). Ça vient de `full_randomizer.py:1029` (`logic.extra_location_requirements`, rempli en parcourant des sets l. 294–325).

Correctif : `{name: sorted(items) for name, items in sorted(...items())}`. Ensuite, ajouter un test qui génère deux fois dans deux processus (`PYTHONHASHSEED` différents) et compare tous les fichiers.

### 5.2 [P1] Release : automatiser « Version X / Rebuild apworld »

Chaque release ajoute à la main les commits `Version 0.8.x` et `Rebuild apworld for 0.8.x` (le binaire `apworld/oot_remake.apworld` est committé). Il faut :
- un script `tools/bump_version.py X.Y.Z` qui met à jour `pyproject.toml` et `__init__.__version__` ;
- reconstruire l'apworld dans `release.yml`. Il faut le jeu pour le catalogue : soit garder le build local mais via une seule commande `tools/release_prep.py` (bump, apworld, tests NUP, contrôle), soit faire construire l'apworld à partir du catalogue committé du §3.4, sans le jeu.

### 5.3 [P2] Harnais de non-régression des sorties (indispensable avant le §4.1)

`tools/golden_seeds.py` : génère 3–4 presets (`ap_defaults`, tout mélangé, adulte, Archipelago), puis écrit un résumé `{chemin: sha256}` de `romfs/` et des JSON normalisés. Un refactor « sans changement de comportement » doit garder ce résumé identique. C'est ce que j'ai fait à la main pour valider le §2.1.

### 5.4 [P3] Divers

- `FEATURES_TODO.md` est ignoré par git, ce qui fait perdre le suivi sur un autre poste. On peut le passer en issues GitHub ou le committer.
- `pyproject` : ajouter `[tool.ruff]` (unused imports, imports locaux en double comme `challenge_steps` et `CHALLENGES`, importés 3 fois dans `generate`) et le lancer en CI. C'est peu coûteux et ça attrape les variables mortes de ce type.
